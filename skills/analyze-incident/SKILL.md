name: analyze-incident
description: 에러·장애의 근본 원인을 분석한다. 에러 로그, 스택 트레이스, 장애 상황을 받아 tracer 에이전트로 원인을 추적하고, historian 에이전트로 관련 코드의 커밋 이력을 조사해 재현 조건을 확정하고 analysis.md를 만든다. 버그 수정 작업의 첫 단계.

에러의 근본 원인을 확정하고 분석 문서를 만든다.
이 단계에서 코드를 수정하지 않는다.

## 0. 작업 ID 확인

인자로 받았으면 사용한다. 없으면 사용자에게 묻는다.

ID로 기존 디렉토리를 먼저 탐색한다 — 티켓이 상위 티켓 디렉토리 안에 중첩될 수 있다:
`find docs/wf -maxdepth 3 -type d -name "*{ID}*"`
- 있으면 그 경로를 이후 모든 `docs/wf/{ID}/` 표기의 실제 경로로 사용한다
- 없으면 상위 티켓 소속인지 사용자에게 확인하고 위치를 정해 만든다
  (상위 소속: `docs/wf/{상위ID}/{ID}-{슬러그}/` · 독립: `docs/wf/{ID}/`)

`docs/wf/{ID}/stage/stage.json` 을 생성한다.

    {
      "id": "{ID}",
      "stage": "analyze-incident",
      "started": "{현재 ISO8601}",
      "expect": "docs/wf/{ID}/analysis.md",
      "allow": []
    }

이 파일이 워크플로우 진입 기록이다.
서브에이전트를 호출하기 전에 만든다.
"id" 에는 docs/wf 기준 상대 경로를 기록한다 (중첩 티켓 예: "쿠폰광고-개발-2356/2369-두레이알림").

## 1. 입력 수집

받은 자료를 아래로 분류한다.

| 자료 | 필수 |
|------|------|
| 상황 설명 (기대/실제 동작, 발생 시점, 영향 범위) | 필수 |
| 스택 트레이스 | 있으면 |
| 트래픽 로그 | 있으면 |
| Log & Crash 로그 | 있으면 |

상황 설명이 없으면 반드시 묻는다.
나머지가 하나도 없으면 "코드만 보고 추적하게 되는데 진행할까요"를 확인한다.

로그 시스템 링크만 있고 본문이 없으면 붙여넣기를 요청한다.
링크는 접근할 수 없다.

## 2. tracer 위임

tracer 서브에이전트에 수집한 자료를 그대로 전달한다.
자료를 요약하거나 편집하지 않는다. 원문을 넘긴다.

전달할 때 다음을 함께 요청한다:
"확신도 판정을 갈라놓는 미확보 관측이 있으면
'결정적 관측' 으로 명시하라 (무엇을, 어디서 조회하면 되는지)."

tracer는 파일을 쓸 수 없다. 보고서를 텍스트로 반환한다.

## 3. 이력 조사 위임 (historian)

tracer 보고서를 받으면 historian 서브에이전트에 커밋 이력 조사를 위임한다.

전달할 것:
- 인과 사슬 각 마디의 위치 (파일:라인)
- "(복원 추정)" 표시된 서술 전체와 그 근거
- 미해결 질문 중 git 이력 관련 항목
- 장애 최초 발생 시각 (있으면)

요청할 것:
- 각 복원 추정의 검증 (일치 / 모순 / 판정 불가)
- 결함 유입 커밋 특정 (해시 · 날짜 · 티켓 · 변경 의도)
- 회귀 여부 판단 (회귀 / 잠복 / 판정 불가)

복원 추정과 git 관련 미해결 질문이 없으면
결함 유입 커밋 특정과 회귀 여부만 요청한다.

historian도 파일을 쓸 수 없다. 보고서를 텍스트로 반환한다.

**되먹임 판정** — historian 보고서를 받으면:

- 추정과 이력이 일치 → 확신도 근거로 반영하고 다음 단계로 간다.
- 추정과 이력이 모순이고, 그 추정이 인과 사슬의 마디였다면 →
  historian이 확인한 사실을 "확정 전제"로 명시해 tracer를 재실행한다.
  재실행은 1회만 한다. 재실행 후에도 모순이 남으면
  사용자에게 두 보고서를 제시하고 판단을 받는다.
- 사슬과 무관한 모순 → 정정 내용만 문서에 기록한다.

## 4. 결과 검토

tracer·historian 보고서를 사용자에게 제시하고 확인받는다.

특히 확인할 것:
- 인과 사슬의 각 마디가 실제 코드 동작과 맞는가
- 확신도가 "가설"인 항목이 있는가
- 놓친 경로가 있는가
- 결함 유입 커밋과 회귀 여부 판단이 실제 배포·작업 이력과 맞는가

사용자가 정정하면 tracer를 다시 돌리지 말고
정정 내용을 분석 문서에 반영한다.
사슬 자체가 틀렸으면 정정된 전제로 tracer를 재실행한다.

## 5. 결정적 관측 게이트

tracer 보고서(또는 검토 결과)에 근본 원인의 확신도를
"유력/가설 → 확정" 으로 올릴 수 있는 미확보 관측이 있으면,
문서를 쓰기 전에 멈추고 사용자에게 그 조회를 요청한다.

요청은 구체적으로 한다. "로그를 더 주세요"가 아니라:
- 무엇을 조회하는가 (예: 해당 시간대 에러 건수와 첫/마지막 발생 시각)
- 어디서 조회하는가 (예: Log & Crash, 배치 로그의 특정 라인, Redis 키 TTL)
- 결과가 무엇을 판별하는가 (예: 전건 실패 = 처음부터 무효 / 도중 전환 = 실행 중 만료)

사용자가 조회 결과를 주면 확신도와 근본 원인 서술에 반영한다.
확보할 수 없다고 하면 미해결 질문으로 남기고 진행한다.
이 게이트를 건너뛰고 "유력"으로 문서화하는 것은
사용자가 명시적으로 그렇게 선택했을 때만 한다.

## 6. 재현 게이트

사용자에게 묻는다: "재현 가능한가요?"

**재현 확보:** 재현 조건(입력, 상태, 환경)을 기록한다.

**재현 미확보:** 아래 중 무엇인지 확인하고 기록한다.
- 로그·메트릭 보강 후 재발 대기
- 운영 데이터로 조건 좁히기 시도
- 근본 원인 미확정 상태로 진행 (방어적 수정)

미확보 상태로 진행하는 것도 정당한 선택이다.
다만 그 선택을 문서에 남긴다. 조용히 넘어가지 않는다.

## 7. 문서 작성

`docs/wf/{ID}/analysis.md` 에 아래 형식으로 저장한다.

---
# [{ID}] {한 줄 제목}

## 입력
제공된 자료 / 미제공 자료

## 발생 지점
예외: (타입 · 메시지)
시작점: /절대/경로/Foo.java:142
실행 맥락:

## 인과 사슬
(tracer 보고서 + historian 검증 + 사용자 정정 반영)

## 근본 원인
(서술)
확신도: 확정 | 유력 | 가설
근거:

## 변경 이력
결함 유입 커밋: {짧은 해시} ({날짜}, {작성자})
티켓·PR:
변경 의도:
회귀 여부: 회귀 | 잠복 | 판정 불가
복원 추정 검증: (일치/모순/판정 불가 요약. 해당 없으면 "해당 없음")

## 재현 조건
확보 | 미확보
(확보면 조건. 미확보면 사유와 선택한 진행 방식)

## 수정 지점 후보
| 마디 | 위치 | 수정 방향 | 성격 | 파급 |

## 미해결 질문

## 이번 조사에서 나온 별건
(조사 중 발견한, 이 티켓과 무관한 문제)

## 8. 종료

문서 경로를 알리고 다음 단계를 안내한다.
"별건"이 있으면 별도 티켓으로 분리할 것을 권한다.

설계는 하지 않는다. 수정 지점을 추천하지 않는다.

산출물 작성을 확인한 뒤 `docs/wf/{ID}/stage/stage.json` 을 삭제한다.
`docs/wf/{ID}/stage/events.log` 에 기록이 있으면 보고에 포함한다.
