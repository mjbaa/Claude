요구사항을 분석 문서로 만든다.
이 단계에서 코드를 수정하지 않는다. 설계도 하지 않는다.

## 0. 작업 ID 확인

인자로 받았으면 사용한다. 없으면 사용자에게 묻는다.
`docs/wf/{ID}/` 디렉토리를 만든다.

`docs/wf/{ID}/stage/stage.json` 을 생성한다.

    {
      "id": "{ID}",
      "stage": "analyze-spec",
      "started": "{현재 ISO8601}",
      "expect": "docs/wf/{ID}/analysis.md",
      "allow": []
    }

이 파일이 워크플로우 진입 기록이다.
서브에이전트를 호출하기 전에 만든다.

## 1. 문서 추출

전달받은 문서를 읽는다.

**먼저 "읽지 못한 영역"을 보고한다.**
- 이미지로 된 화면 설계 (텍스트 추출 불가)
- 표 구조가 깨져 순서를 알 수 없는 부분
- 참조만 있고 실물이 없는 첨부

읽지 못한 영역이 요구사항 이해에 필수적이면
스크린샷이나 텍스트 붙여넣기를 요청한다.
문서가 없고 구두 설명만 있으면 그대로 진행한다.

## 2. 항목화

원문과 해석을 분리해서 표로 만든다.

| ID | 원문 (인용) | 해석 |
|----|------------|------|
| R1 | "상태별로 필터링할 수 있어야 한다" | 쿠폰 상태 필터를 검색 조건에 추가 |

분리하는 이유는 해석 오류를 사용자가 즉시 잡을 수 있게 하기 위함이다.
해석만 적으면 어디서 틀어졌는지 알 수 없다.

요구사항이 여러 개면 반드시 분리한다.
문서 한 건에 기능 여러 개가 섞여 있는 것이 보통이다.

## 3. 존재 확인 게이트

**explorer를 부르기 전에 여기서 먼저 확인한다.**

각 항목이 이미 구현되어 있는지 grep으로 얕게 확인한다.
깊이 파지 않는다. 3~5분 안에 끝낸다.

- 요구사항의 핵심 단어로 클래스·필드·메서드명 검색
- 관련 화면(JSP 등)에 이미 해당 UI가 있는지
- 유사 기능이 인접 도메인에 있는지

결과를 항목별로 사용자에게 제시하고 확인받는다.

| ID | 상태 | 근거 |
|----|------|------|
| R1 | 이미 구현됨 | /절대/경로/Foo.java:30 |
| R2 | 부분 구현 | 백엔드는 있고 UI만 없음 |
| R3 | 미구현 | 관련 코드 없음 |

"이미 구현됨"이 나오면 사용자에게 묻는다:
"이미 있는데 실제 요구는 무엇인가요?"

전부 이미 구현되어 있으면 여기서 종료한다.
explorer를 부르지 않는다.
종료하기 전에 `docs/wf/{ID}/stage/stage.json` 을 삭제한다.

## 4. 미결정 확인

각 항목에서 결정되지 않은 것을 열거한다.
**해결책을 제안하지 않는다.** 무엇이 미결정인지만 적는다.

| # | 미결정 | 왜 중요한가 | 현재 근거 |
|---|--------|------------|----------|
| 1 | 복수 선택 가능? | API 시그니처가 달라짐 | 미확인 |
| 2 | 미지정 시 기본값 | 기존 호출 호환성 | 목록 API는 전체 (추정) |

코드를 봐야 알 수 있는 항목은 3번에서 얻은 정보로 채운다.
기획자에게 물어야 하는 항목은 그렇게 표시한다.

사용자에게 제시하고, 지금 답할 수 있는 것은 답을 받는다.
답 못 하는 것은 "보류"로 명시하고 진행한다.

## 5. 범위 밖 명시

기획 문서에 절대 적혀 있지 않은 항목이다.
여기서 적지 않으면 구현 중에 슬금슬금 늘어난다.

사용자와 함께 "이번에 하지 않을 것"을 정한다.

## 6. explorer 위임

3번에서 "미구현" 또는 "부분 구현"으로 남은 항목만 넘긴다.
이미 구현된 항목은 넘기지 않는다.

요구사항 원문과 2·4번에서 확정된 해석·결정을 함께 전달한다.
요약하지 않는다.

explorer는 파일을 쓸 수 없다. 보고서를 텍스트로 반환한다.

## 7. 결과 검토

explorer 보고서를 사용자에게 제시하고 확인받는다.

특히 확인할 것:
- "현재 동작" 서술이 실제와 맞는가
- 접근 방식 후보에 빠진 것이 있는가
- 영향 범위가 전수인가

사용자가 정정하면 explorer를 다시 돌리지 말고
정정 내용을 문서에 반영한다.
전제 자체가 틀렸으면 정정된 전제로 재실행한다.

## 8. 쟁점 분류

explorer가 낸 설계 쟁점과 4번의 미결정을 합쳐
성격별로 재분류한다.

| 성격 | 뜻 | 처리 |
|------|-----|------|
| 기획 결정 | 제품 동작이 어때야 하는가 | 기획자 확인 필요 |
| 설계 결정 | 구현을 어떻게 할 것인가 | design 단계에서 |
| 확인 필요 | 실행·DB·이력을 봐야 아는 것 | 별도 확인 |

**기획 결정이 남아 있으면 design으로 넘어가지 않는다.**
그 결정에 따라 접근 방식이 갈리기 때문이다.
사용자에게 확인이 필요함을 명시한다.

## 9. 문서 작성

`docs/wf/{ID}/analysis.md` 에 저장한다.

---
# [{ID}] {한 줄 제목}

## 요구사항
| ID | 원문 | 해석 |

## 문서 한계
(읽지 못한 영역. 없으면 "없음")

## 존재 확인
| ID | 상태 | 근거 |

## 현재 동작
(explorer 결과 + 사용자 정정)

## 유사 구현
(위치, 유사점, 그 선례의 결함)

## 접근 방식 후보
| # | 방식 | 손댈 지점 | 파급 | 롤백 |

## 변경 지점
| 계층 | 위치 |

## 영향 범위
| 대상 | 호출 지점 | 종류 |

## 설계 쟁점
### 기획 결정 (design 진입 전 해소 필요)
### 설계 결정
### 확인 필요

## 범위 밖
(이번에 하지 않을 것)

## 별건
(조사 중 발견한, 이 요구사항과 무관한 문제)
---

## 10. 종료

문서 경로를 알린다.

기획 결정이 남아 있으면 그것을 먼저 알린다.
"별건"이 있으면 별도 티켓 분리를 권한다.

접근 방식을 고르지 않는다. 추천하지 않는다.
그것은 design 단계의 일이다.

산출물 작성을 확인한 뒤 `docs/wf/{ID}/stage/stage.json` 을 삭제한다.
`docs/wf/{ID}/stage/events.log` 에 기록이 있으면 보고에 포함한다.
