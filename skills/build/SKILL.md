design.md를 계약으로 삼아 구현하고, 이어서 검증한다.
이 문서 밖의 판단을 하지 않는다.

## 0. 입력 확인

{ID}가 가리키는 디렉토리를 먼저 확정한다 — 티켓이 상위 티켓 디렉토리 안에 중첩될 수 있다:
`find docs/wf -maxdepth 3 -type d -name "*{ID}*"`
이후 모든 `docs/wf/{ID}/` 표기는 확정된 그 디렉토리를 뜻한다.

`docs/wf/{ID}/design.md` 를 읽는다.
없으면 중단하고 design을 먼저 실행하라고 안내한다.

읽은 뒤 아래를 확인하고, 하나라도 없으면 중단한다.
- 변경 지점 목록
- 변경하지 않을 것 목록

"변경하지 않을 것"이 비어 있는 설계는 계약이 아니다.

critic 검토 결과에 "높음" 미해소가 있으면 사용자에게 먼저 알린다.

`docs/wf/{ID}/stage/stage.json` 이 이미 있고 stage 가 build 이면 중단된 작업이다.
progress 와 git diff 를 대조한 뒤,
재개할지 처음부터 다시 할지 사용자에게 확인한다.

## 1. 계약 확인

시작 전에 사용자에게 요약해 보여준다.

- 변경할 파일 N개 (목록)
- 절대 건드리지 않을 것 M개 (목록)

사용자가 진행을 확인하면 `docs/wf/{ID}/stage/stage.json` 을 생성한다.

    {
      "id": "{ID}",
      "stage": "build",
      "started": "{현재 ISO8601}",
      "expect": "docs/wf/{ID}/verify.md",
      "allow": [
        "(design.md 변경 지점의 각 경로)",
        "docs/wf/{ID}/design.md",
        "docs/wf/{ID}/verify.md"
      ],
      "progress": "0/{N}"
    }

allow 는 프로젝트 루트 상대 경로로 적는다.
design.md 자신을 포함시킨다 — 이탈 승인 시 갱신 대상이다.
verify.md 를 포함시킨다 — 8번 검증 문서 작성 대상이다.

이 파일이 편집 차단 훅의 기준이 된다. 생성 후 구현을 시작한다.
이 스킬이 어떤 이유로든 중단되면, 종료 전에 이 파일을 삭제한다.

## 2. 구현

변경 지점을 표에 적힌 순서대로 하나씩 처리한다.
한 번에 여러 지점을 동시에 고치지 않는다.

각 지점마다:
1. 대상 파일의 현재 상태를 읽는다
2. 설계에 적힌 대로만 수정한다
3. 무엇을 바꿨는지 한 줄로 보고한다
4. 다음 지점으로 넘어간다

각 지점 완료 시 stage.json 의 progress 를 갱신한다.

설계에 코드 스케치가 있으면 그것을 기준으로 삼는다.
스케치를 "개선"하지 않는다.
명백한 문법 오류만 바로잡고, 바로잡았으면 보고한다.

## 3. 이탈 처리 (가장 중요)

아래 상황이 발생하면 즉시 멈추고 보고한다.

- 설계 목록에 없는 파일을 수정해야 함
- 설계 목록에 없는 파일을 수정해야 컴파일이 됨
- 설계 스케치가 실제 코드와 맞지 않음
- "변경하지 않을 것" 항목을 건드려야 함

보고 형식:

    [이탈 발생]
    필요한 변경: (무엇을)
    위치: /절대/경로/Foo.java:142
    이유: (왜 필요한가)
    안 하면: (무슨 일이 일어나는가)
    대안: (있으면)

사용자 판단을 기다린다.

승인되면 순서대로 진행한다.
1. design.md 를 갱신한다
2. stage.json 의 allow 에 경로를 추가한다
3. 그 다음 코드를 수정한다

코드보다 문서가 먼저다.

훅에 차단당했다면 그것이 이탈 신호다. 우회를 시도하지 않는다.
사용자 승인 없이 allow 를 수정하는 것은 명백한 실패다.

임의 확장은 명백한 실패다.
"이왕 하는 김에", "이건 당연히 같이", "안 하면 이상하니까" 는 전부 이탈이다.

## 4. 금지

- 요청받지 않은 리팩터링
- 변수명·메서드명 정리
- 미사용 import 제거 (자신이 만든 것 제외)
- 주석 추가·수정 (설계에 명시된 것 제외)
- 포맷팅 변경
- "변경하지 않을 것" 목록의 모든 항목

주변 코드에서 문제를 발견해도 고치지 않는다.
발견 사항으로 기록하고 넘어간다.

## 5. 컴파일 확인

IDE 빌드 툴을 우선 사용한다.

    mcp__idea__build_project
    - filesToRebuild 에 변경한 파일 경로만 지정 (프로젝트 루트 상대 경로)
    - rebuild 는 false 유지

호출이 실패하면 (IntelliJ 미실행, 프로젝트 미개방, 서버 연결 끊김)
그 사실을 보고하고 프로젝트 관례에 따라 빌드 명령을 직접 실행한다.
어느 경로로 확인했는지 보고에 명시한다.

컴파일 실패 시:
- 설계 범위 내 수정으로 해결되면 고친다
- 설계 밖 수정이 필요하면 3번 이탈 처리로 간다

여기서 테스트를 직접 돌리지 않는다. 테스트 실행은 6번에서 verifier가 수행한다.

## 6. 검증 위임 (scope-auditor·verifier 병렬)

컴파일 확인이 끝나면 검증으로 자동 진행한다. 별도 사용자 확인을 받지 않는다.
단, 해소되지 않은 이탈 보고가 있으면 그것부터 사용자 판단을 받는다.

scope-auditor 와 verifier 서브에이전트를 **한 메시지에서 동시에** 호출한다 (병렬 실행).
구현을 수행한 이 컨텍스트가 스스로 검증을 대신하지 않는다 —
검증의 가치는 구현자와 다른 눈에서 나온다.

- scope-auditor 에 전달: design.md 경로 (설계-diff 기계 대조를 맡긴다)
- verifier 에 전달: design.md 경로, 변경 파일 목록,
  구현 중 "verify에서 확인 필요"로 넘긴 항목 (정적 분석 + 테스트 실행을 맡긴다)

두 에이전트 모두 파일을 쓸 수 없다. 보고서를 텍스트로 반환한다.
두 보고서가 모두 도착할 때까지 다음 단계로 넘어가지 않는다.

## 7. 검증 결과 처리 (게이트)

두 보고서를 사용자에게 제시한다.

**scope-auditor 결과:**
- 금지 목록 위반 → 먼저 알린다. 계약 위반이므로 되돌릴지 승인할지 사용자가 정한다
- 초과 변경 → 성격별 처리:
  - 컴파일 필수 → design.md에 사후 추가하고 기록
  - 부수 정리 → 되돌릴지 유지할지 사용자 판단
  - 임의 개선 → 되돌리기 권고. 유지하려면 이유를 기록
  - 무관 → 되돌리기
- 누락 → 의도된 것인지 확인

**verifier 결과:**
- 이번 변경이 만든 문제 → 설계 범위 내면 수정하고, 범위 밖이면 3번 이탈 처리
- 기존 부채 → 기록만. 고치지 않는다 (요청받지 않은 리팩터링이다)
- 오탐 → 근거를 확인하고 기록
- "판정 필요" 항목 → 사용자에게 묻는다
- 테스트 실패 → 구현 문제면 위와 동일하게 수정, 테스트 코드·설계 서술 문제면 사용자에게 알린다

위반·초과·누락·신규 문제·테스트 실패·판정 필요가 **모두 0건이면
게이트 없이 8번으로 진행한다.**

이 단계에서 코드를 수정했으면 5번(컴파일)부터 다시 수행하고,
6번 검증을 재위임한다. 재검증 없이 수정을 통과시키지 않는다.

## 8. verify.md 작성

docs/wf/{ID}/verify.md 에 저장한다.

    # [{ID}] 검증 결과

    ## 요약
    스코프: 초과 N건 / 누락 M건 / 금지 위반 K건
    정적 분석: 신규 N건 / 기존 부채 M건 / 오탐 K건
    자동 테스트: 통과 N건 / 실패 M건
    판정: 통과 | 조건부 통과 | 실패

    ## 스코프 대조
    | 구분 | 항목 | 위치 | 상태 | 처리 |

    ## 금지 목록
    | 항목 | 위반 | 근거 |

    ## 정적 분석
    실행: IDE inspection | 건너뜀 (사유)

    | 파일 | 심각도 | 내용 | 분류 | 처리 |

    오탐 판정 근거:
    (각 오탐마다 왜 오탐인지)

    ## 자동 테스트
    | 테스트 | 결과 | 비고 |

    ## 수동 확인 (사용자 직접)
    - [ ] 항목 — 무엇을 어떻게 / 실패 판정 기준

    ## 확인 필요 (미해소)
    | 항목 | 상태 | 확인 방법 |

    ## 구현 중 발견 사항
    (별건으로 처리할 것. 기존 부채 포함)

    ## 남은 작업
    (있으면. 없으면 "없음")

수동 확인 항목은 design.md의 수동 검증 항목을 체크리스트로 만든다.
각 항목에 무엇을 어떻게 보면 되는지 구체적으로 적고, 실패 판정 기준을 명시한다.
"화면에서 확인" 같은 모호한 표현을 쓰지 않는다.

design.md의 "확인 필요" 표를 검토한다.
구현 또는 검증으로 해소된 것은 결과를 기록하고, 여전히 미확인이면 그대로 남긴다.

    ### 변경한 지점
    | # | 위치 | 무엇을 |

    ### 이탈
    (있으면 무엇을 왜 어떻게 처리했는지. 없으면 "없음")

    ### 미구현
    (설계에 있으나 하지 않은 것과 이유. 없으면 "없음")

    ### 컴파일
    성공 | 실패 (사유)
    확인 경로: IDE 빌드 | 직접 빌드 명령

    ### 검증 요약
    (verify.md의 요약 절 그대로 + verify.md 경로)

    ### 수동 확인 (사용자 직접)
    (체크리스트)

    ### 구현 중 발견 사항
    (고치지 않고 기록만 한 것)

보고 후 승격을 안내한다.

모듈 CLAUDE.md로 승격할 후보
- 구현 중 발견한 함정이나 숨은 의존
- 반복될 오탐의 근거 (다음 사람이 같은 판단을 하도록)
- 다음 사람이 모르면 같은 실수를 할 지점

별도 티켓 후보
- analysis.md와 verify.md의 "별건" 항목
- 정적 분석에서 나온 기존 부채

정리 대상
- docs/wf/{ID}/ 는 작업 종료 후 아카이브 또는 삭제
- 남길 것은 위 두 곳으로 승격한 뒤 지운다

승격 여부는 사용자가 정한다. 자동으로 파일을 옮기지 않는다.

verify.md 작성을 확인한 뒤 `docs/wf/{ID}/stage/stage.json` 을 삭제한다.
`docs/wf/{ID}/stage/events.log` 에 BLOCK 기록이 있으면 보고에 차단 건수를 포함한다.
