분석 결과를 기능 단위 명세로 확정한다.
이 단계에서 코드를 수정하지 않는다. 심볼 단위 설계는 design의 일이다.

## 0. 입력 확인

{ID}가 가리키는 디렉토리를 먼저 확정한다 — 티켓이 상위 티켓 디렉토리 안에 중첩될 수 있다:
`find docs/wf -maxdepth 3 -type d -name "*{ID}*"`
이후 모든 `docs/wf/{ID}/` 표기는 확정된 그 디렉토리를 뜻한다.

`docs/wf/{ID}/analysis.md` 를 읽는다.
없으면 중단하고 analyze-incident 또는 analyze-spec을 먼저 실행하라고 안내한다.

`docs/wf/{ID}/stage/stage.json` 을 생성한다.

    {
      "id": "{ID의 docs/wf 기준 상대 경로}",
      "stage": "spec",
      "started": "{현재 ISO8601}",
      "expect": "docs/wf/{ID}/spec.md",
      "allow": []
    }

이 파일이 워크플로우 진입 기록이다.
서브에이전트를 호출하기 전에 만든다.
이 스킬이 어떤 이유로든 중단되면, 종료 전에 이 파일을 삭제한다.

## 1. 구조 확정 (게이트)

analysis.md의 접근 방식 후보를 사용자에게 제시한다.
추천하지 않는다. 각 안의 파급·롤백을 나란히 놓는다.
사용자가 의견을 물으면 그때 근거와 함께 답한다.

**사용자가 고를 때까지 다음 단계로 넘어가지 않는다.**

이 논의는 한 번에 끝나지 않는 것이 보통이다.
사용자가 사실을 더 요구하면 (기존 코드의 실물, 인접 시스템의 처리 방식 등)
조사해서 답하고, 그 사실이 후보 구도를 바꾸면 바뀐 구도를 다시 제시한다.
논의 중 잘못 말한 것이 드러나면 정정한다고 명시하고 고친다.

확정되면 기록한다:
- 선택한 구조 — 호출 관계 다이어그램 수준
- 기각한 안과 사유 — 각각 한 줄 이상. design이 이것을 승계한다

기획 결정이 필요한 미확정이 구조 선택을 가르면 여기서 중단한다.
가르지 않으면 5번의 "전제·미확정"에 등재하고 진행한다.

## 2. conventions 위임

명세에 등장할 요소 목록을 뽑아 conventions 서브에이전트에 넘긴다.
- 신규 클래스·메서드 (네이밍·위치)
- 빈 등록·설정 주입 방식
- 프로퍼티 키 표기
- 잡·API 등 단위 추가 골격
- 가장 가까운 선례와 그 결함

확정된 구조와 함께 전달한다. 요약하지 않는다.
conventions는 파일을 쓸 수 없다. 보고서를 텍스트로 반환한다.

## 3. 관례 정렬

conventions 보고대로 명세의 모든 이름·위치·키를 정렬한다.
근거는 명세에 괄호로 축약해 남긴다 — 선례 클래스명 수준. 논증 문단을 쓰지 않는다.

관례가 없거나(선례 없음) 관례를 벗어나야 하는 요소는
그 사실을 사용자에게 알리고 확인받는다.
신규 패턴 도입은 사용자의 결정이지 기본값이 아니다.

## 4. 기능 표 작성

형식 규칙:
- 기능 열: `{배포 단위} : {기능명}` — 모듈·레포가 다르면 행을 나눈다
- 내용 열: 선언 문장("~한다.") + `ㄴ` 사실 나열
- ㄴ 한 줄 = 사실 하나. 시그니처·필드·조건·값 수준까지 적는다
- 설계 논증을 쓰지 않는다. 필요한 근거는 괄호 한 마디로 (예: "(DoorayResourceMonitorAlert 관례)")
- 번호는 원문자(①②) 대신 숫자로 쓴다
- 여러 기능이 공유하는 컴포넌트는 자기 행을 갖고, 호출처 행은 호출 방법만 적는다
- 타 파트·타 레포 몫은 기능명에 "(구현은 ○○ — 이 문서는 계약 정의)"를 명시한다

깊이의 기준은 아래 모범 행이다. 이보다 얕으면 (조건·시그니처 생략) 계약이 못 되고,
이보다 깊으면 (근거 문단, 대안 논증) design 문서가 된다.

    | **payco-event batch : 미정산 리마인드 배치** | 매월 25일~말일 일 1회(오전), 정산 미완료 건 리마인드를 발송한다.<br>
    ㄴ 신규 batch 잡을 작성한다<br>
    ㄴ 정산 예정일이 당월 20일인 건 중 '정산 완료' 미처리 건을 조회한다 (정산 테이블 스키마 확정 후 구현)<br>
    ㄴ settleAlert.sendRemind(요약, 멘션 멤버 ID)를 동기 호출하고, 예외를 그대로 전파한다 — try-catch로 삼키지 않는다 (예외 전파 시 공통 실패 리스너가 release 환경에서 incident 자동 등록 — 별도 실패 알림 구현 불필요)<br>
    ㄴ 대상 0건이면 발송하지 않는다<br>
    ㄴ 잡 내 재시도 X — 일 1회 재실행이 자연 재시도 |

문장 구조를 보라: 첫 문장은 언제·무엇을 한다, ㄴ은 각각 하나의 사실(할 일·조건·시그니처·정책),
근거는 괄호 안 한 호흡, "왜 이 방식인가"는 없다 — 그것은 확정 구조와 기각 줄의 몫이다.

메시지·화면·응답처럼 산출 형식이 있으면 "포맷 정의" 행을 첫 행으로 둔다.
구현이 흩어져도 포맷의 기준은 문서 한 곳이어야 한다.

## 5. 전제·미확정 + 변경하지 않는 것 (필수)

**이 두 절이 비어 있으면 문서를 완성하지 않는다.**

전제·미확정: `| # | 항목 | 상태 |` — 이후 해소되면 행을 지우지 말고 상태를 갱신한다.
변경하지 않는 것: 재사용만 할 기존 코드, 무접촉 대상, 인지 후 수용한 리스크.

## 6. 검토 게이트

문서 전체를 사용자에게 제시하고 확인받는다.
- 표현·깊이 정정은 반영한다
- 구조가 바뀌는 정정이면 1번으로 돌아간다

## 7. 문서 작성

`docs/wf/{ID}/spec.md` 에 저장한다.

---
# [{ID}] 기능 명세서 — {한 줄 제목}

(상위 이슈가 있으면: 상위 이슈: {상위ID} — 공용 문서는 상위 디렉토리 참조)
(요구사항 원문 출처 한 줄)

## 확정 구조 ({날짜})

(선택한 구조 한 문단 + 호출 관계 다이어그램)

## 8. 종료

문서 경로를 알린다.
design 진입을 가르는 미확정이 남아 있으면 그것을 먼저 알린다.

구현하지 않는다. 심볼 단위 변경 지점을 확정하지 않는다. 그것은 design의 일이다.

산출물 작성을 확인한 뒤 `docs/wf/{ID}/stage/stage.json` 을 삭제한다.
`docs/wf/{ID}/stage/events.log` 에 기록이 있으면 보고에 포함한다.
