기획이 개발 가능한 수준으로 정리되었는지 검토한다.
상세 설계를 하지 않는다. 코드를 수정하지 않는다.

산출물은 기획자에게 회신할 문서다. 개발 내부 문서가 아니다.

## 0. 범위 확인

아래를 사용자에게 확인한다. 한 번에 하나씩 묻는다.

1. 작업 ID — 없으면 `{YYYYMMDD}-{기능명}` 형식으로 정한다
2. 기획서 파일 경로 — 여러 개면 전부. 각 파일이 무엇인지도 확인한다
3. 담당 파트 — 여러 군데면 전부 나열받는다.
   "이 부분과 저 부분" 처럼 흩어져 있는 것이 정상이다

담당 파트가 하나인지 여러 개인지 먼저 확인한다.
여러 개면 각각을 독립 항목으로 다룬다. 하나로 뭉치지 않는다.

3번을 모르면 진행하지 않는다. 검토 범위가 정해지지 않으면
전체를 검토하게 되고, 남의 파트에 대한 지적은 회신에 쓸 수 없다.

ID로 기존 디렉토리를 먼저 탐색한다 — 티켓이 상위 티켓 디렉토리 안에 중첩될 수 있다:
`find docs/wf -maxdepth 3 -type d -name "*{ID}*"`
- 있으면 그 경로를 이후 모든 `docs/wf/{ID}/` 표기의 실제 경로로 사용한다
- 없으면 상위 티켓 소속인지 사용자에게 확인하고 위치를 정해 만든다
  (상위 소속: `docs/wf/{상위ID}/{ID}-{슬러그}/` · 독립: `docs/wf/{ID}/`)

`docs/wf/{ID}/stage/stage.json` 을 생성한다.

    {
      "id": "{ID}",
      "stage": "review-spec",
      "started": "{현재 ISO8601}",
      "expect": "docs/wf/{ID}/review.md",
      "allow": []
    }

이 파일이 워크플로우 진입 기록이다.
서브에이전트를 호출하기 전에 만든다.
이 스킬이 어떤 이유로든 중단되면, 종료 전에 이 파일을 삭제한다.

## 1. 문서 읽기

기획서 전체를 읽는다. 담당 파트만 읽지 않는다.
담당 파트의 전제와 제약이 다른 파트에 적혀 있는 경우가 많다.

기획서가 여러 개면 전부 읽는다. 그리고 문서 간 관계를 파악한다.
- 버전 관계인가 (구버전 / 신버전)
- 파트 분할인가 (화면 기획서 / API 명세 / 데이터 정의)
- 별개 기능인가

버전 관계면 어느 것이 최신인지 사용자에게 확인한다.
문서 간 내용이 상충하면 해당 항목의 "추가 확인"에 기록한다.
어느 쪽이 맞는지 스스로 판단하지 않는다.

HTML 기획서는 아래를 주의한다.
- 스타일·스크립트 블록은 무시한다
- 이미지로 된 화면 설계는 텍스트 추출이 되지 않는다
- 표는 구조가 깨져 순서가 뒤바뀔 수 있다
- 접힌 영역(details, accordion)이나 탭 안의 내용을 놓치기 쉽다

먼저 "읽지 못한 영역"을 보고한다.
- 이미지로만 존재하는 부분 (위치와 추정 내용)
- 구조가 깨져 해석이 불확실한 표
- 링크만 있고 실물이 없는 참조

읽지 못한 영역이 담당 파트 이해에 필수적이면
스크린샷이나 텍스트 붙여넣기를 요청한다. 추측으로 채우지 않는다.

## 2. 담당 항목 분해 (게이트)

담당 파트를 독립적으로 판단 가능한 항목 단위로 쪼갠다.
파트가 하나여도 성격이 다른 것이 섞여 있으면 나눈다.

기준: 각 항목이 서로 다른 시스템·모듈·담당자에 걸리는가.

| 항목 | 기획서 위치 | 내용 요약 |
|------|------------|----------|
| A    | 문서1 3장   |          |
| B    | 문서2 2.1절 |          |

기획서 전체의 파트 구조도 함께 제시한다.
담당 밖 파트는 경계 검토에 쓴다.

| 파트 | 내용 요약 | 담당 |
|------|----------|------|
|      |          | 나 / 타 파트 / 미정 |

항목 분해와 담당 경계가 사용자 인식과 맞는지 확인받는다.
"미정"이 있으면 지적한다 — 담당 미정은 그 자체로 검토 항목이다.

사용자 확인 없이 2-1로 넘어가지 않는다.

### 2-1. 항목별 프로젝트 관련성 판정 (게이트)

각 담당 항목이 현재 레포에 해당하는지 개별로 판정한다.
파트 전체에 대해 하나로 판정하지 않는다.

현재 레포의 CLAUDE.md와 모듈 구성을 읽고, 각 항목의
기능·화면·API·도메인 용어가 이 레포에 존재하는지 얕게 확인한다.
grep 몇 번으로 끝낸다. 깊이 파지 않는다.

신규 기능은 코드가 없는 것이 정상이다.
기능의 존재가 아니라 도메인이 이 레포에 속하는지로 판정한다.

| 항목 | 판정 | 근거 |
|------|------|------|
| A | 이 레포 | 관련 도메인·클래스 존재 (경로) |
| B | 타 시스템 | 이 레포에 관련 도메인 없음. {짐작되는 시스템} |
| C | 걸침 | 이 레포 + 외부 연동 |
| D | 불명 | 판단 근거 부족 |

판정 결과를 사용자에게 제시하고 확인받는다.
"불명"이 있으면 사용자에게 어디 소속인지 묻는다.

**모든 항목이 "타 시스템"이면** 여기서 중단한다.
- 무엇을 찾았고 무엇을 못 찾았는지 알린다
- 어느 레포에서 다시 실행해야 할지 짐작되면 알린다
- `docs/wf/{ID}/stage/stage.json` 을 삭제하고 종료한다. 문서를 만들지 않는다

**일부가 "이 레포"이면** 진행한다. 이후 단계에서:
- "이 레포" 항목만 관점 1~4로 검토한다
- "타 시스템" 항목은 검토하지 않는다.
  대신 경계 검토(5번)와 "검토 범위 밖" 섹션에 남긴다
- "걸침" 항목은 이 레포 쪽만 검토하고,
  외부 부분은 "확인 필요"로 남긴다

이 판정 없이 surveyor 를 호출하지 않는다.
무관한 항목을 조사하면 "관련 코드 없음"이 대량 반환되고,
그것이 "영향 없음"으로 잘못 해석된다.

## 3. surveyor 위임

2-1에서 "이 레포" 또는 "걸침"으로 판정된 항목에서만
기능·화면·API·데이터 이름을 목록으로 뽑는다.

"타 시스템" 항목의 이름은 넘기지 않는다.

surveyor 서브에이전트에 그 목록을 전달한다.
기획서 전문을 넘기지 않는다. 확인할 항목만 넘긴다.

surveyor는 파일을 쓸 수 없다. 보고서를 텍스트로 반환한다.

보고서의 "심층 조사 필요" 항목은 해당 항목의 "추가 확인"에 반영한다.
여기서 다시 파고들지 않는다.

## 4. 다섯 관점 검토

"이 레포" 및 "걸침" 항목을 아래 다섯 관점으로 본다.
관점은 검토할 때 쓰는 렌즈이고, 산출물은 관점이 아니라
**항목(기능·화면) 단위로 묶는다** (7번 템플릿 참고).
각 지적은 결론이 아니라 질문 형태로 적는다.
판단이 애매한 것을 단정하지 않는다.

### 관점 1 — 기획 홀

기획서에 적혀 있지 않아 개발할 수 없는 것.

- 예외·실패 시 동작 (없는 데이터, 권한 없음, 외부 호출 실패)
- 경계값 (0건, 최대값, 만료 시점)
- 기본값 (미입력, 미선택 시)
- 상태 전이 (어떤 상태에서 어떤 상태로 갈 수 있는가)
- 권한 (누가 볼 수 있고 누가 바꿀 수 있는가)
- 데이터 수명 (언제 생기고 언제 사라지는가)

"안 적혀 있다"와 "당연해서 안 적었다"를 구분하지 않는다.
개발자가 임의로 정하게 되는 것은 모두 홀이다.

### 관점 2 — 개발 걸림돌

기획대로 만들기 어렵거나 비용이 큰 지점.

- 기존 구조와 상충하는 요구
- 성능상 무리가 있는 조회·처리
- 외부 시스템 의존 (연동 계약이 필요한가)
- 데이터 마이그레이션이 필요한 변경
- 되돌리기 어려운 결정 (스키마, 외부 계약)

"불가능하다"가 아니라 "이렇게 하면 비용이 크니 확인이 필요하다"로 쓴다.

### 관점 3 — 사이드이펙트

기존 코드·기능에 미치는 영향. surveyor 보고서를 근거로 쓴다.

- 기존 화면·API의 동작이 바뀌는가
- 같은 데이터를 쓰는 다른 기능이 있는가
- 기존 사용자의 기대가 어긋나는가
- 배치·스케줄러 등 눈에 안 보이는 소비자가 있는가

코드로 확인한 것과 추정을 구분한다. 추정은 "(추정)" 표시.

### 관점 4 — 구현 방향

각 항목을 어떤 방향으로 만들 수 있을지 개략 수준으로 적는다.
기획자가 규모와 제약을 판단할 수 있게 하는 것이 목적이다.

**적을 것**

- 처리 위치 — 어느 계층·모듈에서 처리하는가
  (화면 / API / 서비스 / 배치 / 외부 연동)
- 기존 확장인가 신규 제작인가
- 데이터 — 기존 테이블 확장 / 신규 저장 필요 / 저장 없이 계산
- 처리 방식 — 동기 응답 / 비동기 / 배치. 즉시성이 필요한가
- 규모 감각 — 작음 / 보통 / 큼. 반드시 근거를 함께 적는다
  (예: "큼 — 신규 테이블 + 배치 + 화면 3개")
- 이 방향을 택하면 생기는 제약 — 기획 판단에 직결되는 부분
  (예: "배치로 처리하면 등록 즉시 반영되지 않는다")
- 복잡한 처리는 3~5단계 순서와 실패 지점

대안이 있으면 나열한다. 비교하거나 추천하지 않는다.
방향이 하나로 보이면 그렇게 적되, "유일하다"고 단정하지 않는다.

**적지 않을 것 (design 단계의 일)**

- 클래스명·메서드명·변수명
- 변경할 파일과 라인
- 코드 스케치
- 방식 간 비교와 기각 사유
- 변경하지 않을 것

서술은 "이 방향으로 가능해 보인다" 수준으로 쓴다.
"이렇게 구현한다"로 단정하지 않는다.
실제 방식은 design 단계에서 확정된다.

surveyor 보고서에서 확인된 현행 구조를 근거로 쓴다.
확인하지 못한 것에 근거한 방향은 "(확인 필요)"를 붙인다.

### 관점 5 — 추가 확인 필요

위 넷에 들어가지 않는 확인 항목.

- 기획 의도가 불명확한 문장
- 다른 파트와 상충하는 것으로 보이는 서술
- 문서 간 상충하는 내용
- 운영 데이터를 봐야 판단되는 것
- 유관 부서 확인이 필요한 것
- surveyor 가 "심층 조사 필요"로 남긴 것
- "걸침" 항목의 외부 연동 부분

## 5. 경계 검토

담당 항목 사이, 그리고 담당과 다른 파트 사이를 본다.
가장 값진 발견이 여기서 나온다.

- 내 항목이 다른 파트의 산출물을 전제하는가. 그 산출물 형태가 정해졌는가
- 다른 파트가 내 항목의 동작을 전제하는가
- "타 시스템"으로 넘긴 항목이 내 항목에 영향을 주는가
- 같은 것을 양쪽에서 다르게 부르고 있지 않은가
- 양쪽 다 안 하기로 되어 있는 회색 지대가 있는가
- 담당이 "미정"인 항목이 내 항목에 영향을 주는가

경계 문제는 담당자끼리 합의가 필요하므로 "합의 필요 대상"을 반드시 적는다.
특정 항목에 귀속되는 경계는 그 항목의 "추가 확인 · 파트 경계"에,
어느 항목에도 붙지 않는 것은 "항목 횡단" 섹션에 둔다.

## 6. 심각도 분류

각 항목에 심각도를 부여한다. 기획자가 우선순위를 알아야 한다.

| 심각도 | 뜻 |
|--------|-----|
| 차단 | 이것이 정해지지 않으면 개발을 시작할 수 없다 |
| 확인 | 개발은 시작할 수 있으나 진행 중 정해져야 한다 |
| 참고 | 알고 있으면 좋은 것. 지금 답이 없어도 된다 |
| 해소 | 회신·후속 결정으로 닫힘. 삭제하지 않고 남긴다 |

"차단"을 남발하지 않는다.
임의로 정하고 나중에 바꿀 수 있는 것은 "확인"이다.

기획 회신이나 개발 리뷰 결정이 오면 해당 지적을 지우지 말고
[해소]로 바꾸고 결정 내용·날짜를 병기한다 — 왜 닫혔는지가 이력이다.
요약 아래 "회신 반영" 표에 결정 → 영향 매핑도 함께 남긴다.

## 7. 문서 작성

`docs/wf/{ID}/review.md` 에 저장한다.

**항목(기능·화면) 단위로 묶는다.** 관점별로 장을 나누지 않는다 —
같은 화면의 홀·걸림돌·구현 방향이 흩어지면 기획자가 화면 단위로 회신할 수 없다.
관점은 각 항목 안의 소제목이다.

    # [{ID}] 기획 검토 — {기능명}

    검토 범위: {이 레포에 해당하는 항목만}
    기획서: {파일 목록}
    검토일: {날짜}

    ## 요약
    차단 N건 / 확인 M건 / 참고 K건
    (개발 착수 가능 여부 한 줄.
     착수 초기에 확정이 필요한 것이 있으면 번호 목록으로 2~3건까지)

    (회신·후속 결정이 반영된 뒤에는 여기에 "회신 반영" 표 추가:
     | 결정 | 내용 | 이 문서에 미친 영향 | )

    ## 문서 한계
    (읽지 못한 영역. 없으면 "없음")

    - [확인] {질문 형태의 지적} → {누가 답할 수 있는가}

    ## 항목 횡단
    (어느 항목에도 붙지 않는 경계·확인 사항. 없으면 생략)
    (전체 규모 감각 한 줄 — 예: "큼 — 화면 6종 + 배치 + 신규 테이블 다수")

    ## 검토 범위 밖
    (타 시스템 항목. 담당자·확인 경로가 짐작되면 함께)

    ## 개발 측 메모 (기획자 회신 제외)
    - analyze-spec 단계에서 깊게 볼 것
    - 코드 확인 중 발견한 별건

각 지적 앞에 [차단]/[확인]/[참고]/[해소] 마커를 붙인다.
요약의 건수는 어림하지 말고 본문 마커를 실제로 세어 적는다 —
수정을 거듭하면 요약과 본문이 어긋나기 쉬우니, 본문을 고칠 때마다 재집계한다.
항목 안에서 해당 관점에 지적이 없으면 소제목을 지우지 말고 "없음"으로 적는다 —
안 본 것과 봤는데 없는 것을 구분하기 위함이다.

## 8. 종료

문서 경로를 알린다.
"차단" 항목이 있으면 그것을 먼저 알린다.
"검토 범위 밖" 항목이 있으면 누가 검토해야 하는지 확인을 권한다.

"개발 측 메모" 섹션은 기획자 회신에서 제외해야 함을 알린다.

구현 방향은 개략 판단이며 실제 방식은 design 단계에서 확정된다는 점을 알린다.

설계하지 않는다. 변경 지점을 특정하지 않는다.
그것은 analyze-spec 과 design 단계의 일이다.

산출물 작성을 확인한 뒤 `docs/wf/{ID}/stage/stage.json` 을 삭제한다.
`docs/wf/{ID}/stage/events.log` 에 기록이 있으면 보고에 포함한다.
