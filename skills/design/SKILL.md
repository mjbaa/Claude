접근 방식을 확정하고 구현 계약 문서를 만든다.
이 단계에서 코드를 수정하지 않는다.

## 0. 입력 확인

`docs/wf/{ID}/analysis.md` 를 읽는다.
없으면 중단하고 analyze-incident 또는 analyze-spec을 먼저 실행하라고 안내한다.

`docs/wf/{ID}/stage/stage.json` 을 생성한다.

    {
      "id": "{ID}",
      "stage": "design",
      "started": "{현재 ISO8601}",
      "expect": "docs/wf/{ID}/design.md",
      "allow": []
    }

이 파일이 워크플로우 진입 기록이다.
서브에이전트를 호출하기 전에 만든다.
이 스킬이 어떤 이유로든 중단되면, 종료 전에 이 파일을 삭제한다.

## 1. 기획 결정 확인 (게이트)

analysis.md의 "설계 쟁점 > 기획 결정"을 확인한다.

미해소 항목이 있으면 사용자에게 알린다.
- 해소되었으면 결정 내용을 받아 기록한다
- 이번 범위 밖이면 "범위 밖"으로 명시하고 진행한다
- 여전히 미정이고 접근 방식 선택에 영향을 주면 여기서 중단한다

기획 결정이 접근 방식을 가르는 경우, 그것을 먼저 정하지 않고 진행하면
설계를 두 번 하게 된다.

"범위 밖"으로 두는 결정이 기존 기능을 퇴화시키지 않는지 확인한다.
화면 노출과 백엔드 지원은 별개로 다룰 수 있다.

## 2. 접근 방식 선택 (게이트)

analysis.md의 접근 방식 후보를 사용자에게 제시한다.

**추천하지 않는다.** 사실만 정리해서 보여준다.
각 안의 파급과 롤백 난이도를 나란히 놓아 사용자가 판단하게 한다.

후보가 2개 미만이거나 전부 같은 성격이면
그 사실을 알리고 다른 축의 방식이 없는지 함께 검토한다.

**사용자가 고를 때까지 다음 단계로 넘어가지 않는다.**

고른 뒤 확인한다.
- 선택한 안
- 기각 사유 — 나머지 안을 왜 안 골랐는가. 각각 한 줄 이상

기각 사유는 이 문서에서 가장 오래 살아남는 부분이다.
다음에 비슷한 요구가 왔을 때 "그때 왜 안 했더라"에 답한다.

## 3. 설계 결정 해소

analysis.md의 "설계 결정" 항목을 하나씩 처리한다.

각 항목에 대해 선택지와 근거를 제시하고 사용자 판단을 받는다.
사용자가 위임하면 결정하되, 무엇을 왜 그렇게 정했는지 기록한다.

"확인 필요" 항목은 여기서 해소하지 않는다.
확인 방법과 확인 전 가정을 기록하고 넘어간다.

## 4. 변경 지점 확정

파일 단위가 아니라 **심볼 단위**로 적는다.
"SearchParam 수정"이 아니라 "SearchParam#status 필드 타입 교체".

각 지점에: 위치(절대 경로:라인) / 무엇을 / 유형(추가·수정·삭제·신규).

analysis.md의 변경 지점을 그대로 옮기지 않는다.
선택한 방식에 맞게 확정한다.

## 5. 변경하지 않을 것 확정 (필수)

**이 항목이 비어 있으면 문서를 완성하지 않는다.**

"변경 없는 파일"과 "변경하지 않을 것"은 다르다.
전자는 관찰이고 후자는 금지다. 후자를 적는다.

포함할 것:
- 건드리면 안 되는 인접 코드
- 눈에 띄지만 이번에 고치지 않을 것
- 리팩터링 유혹이 있는 지점
- analysis.md의 "범위 밖" 항목

구현 에이전트는 주변 코드를 "개선"하려는 성향이 강하다.
명시적 금지 목록이 없으면 스코프가 늘어난다.

## 6. critic·side-effect 병렬 위임

critic과 side-effect 서브에이전트를 **한 메시지에서 동시에** 호출한다 (병렬 실행).
두 보고서가 모두 도착할 때까지 다음 단계로 넘어가지 않는다.

두 에이전트 모두에 아래를 전달한다.
- 선택한 접근 방식과 이유
- 변경 지점 목록
- 변경하지 않을 것 목록
- analysis.md의 현재 동작·영향 범위

역할 구분 (프롬프트에 명시한다):
- critic — 설계의 결함을 반박한다. 심각도 부여.
- side-effect — 적용 시 시스템 변화(사라짐·바뀜·유지)를 판정 없이 전수 열거한다.

두 에이전트 모두 파일을 쓸 수 없다. 보고서를 텍스트로 반환한다.

## 7. 지적 반영

critic 보고서와 side-effect 보고서를 사용자에게 제시한다.

심각도별 처리를 사용자와 정한다.
- 높음 — 해소하거나, 해소 못 하면 접근 방식을 재검토한다
- 중간 — 설계에 반영하거나 "인지 후 진행"으로 기록
- 낮음 — 기록만

반박을 무시하는 것도 선택이다. 다만 무시했다는 사실과 이유를 남긴다.

critic 지적으로 접근 방식이 바뀌면 2번으로 돌아간다.

side-effect 보고서는 심각도 처리 대상이 아니다.
- 변화 사실은 설계 문서의 "사이드이펙트 조사 결과"에 기록한다
- 후속 확인이 필요한 항목은 "확인 필요"로 등재한다
- 범위 밖 발견은 별건으로 기록한다
- critic 지적과 겹치는 변화는 critic 쪽 처리에 따른다

처리 방침을 추천하지 않는다. "Recommended" 같은 라벨을 붙이지 않는다.
선택지와 각각의 결과만 제시하고 사용자가 고르게 한다.

`docs/wf/{ID}/design.md` 에 저장한다.

## 9. 종료

문서 경로를 알린다.
critic 지적 중 "높음"이 미해소로 남아 있으면 그것을 먼저 알린다.

구현하지 않는다. 코드를 쓰지 않는다.

산출물 작성을 확인한 뒤 `docs/wf/{ID}/stage/stage.json` 을 삭제한다.
`docs/wf/{ID}/stage/events.log` 에 기록이 있으면 보고에 포함한다.
